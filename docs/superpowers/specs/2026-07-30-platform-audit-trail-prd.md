# SADC PF Nexus

# Platform Audit Trail, Activity Monitoring & Forensic Event Register

## Full Updated Product Requirements Document

**System:** SADC PF Nexus Internal Paperless Administration System
**Module:** Platform Audit Trail, Activity Monitoring & Forensic Event Register
**Short name:** Audit Trail
**Document status:** Updated implementation PRD
**Module type:** Shared immutable event-recording, security-monitoring, accountability and forensic-evidence service

The next module is **Platform Audit Trail, Activity Monitoring & Forensic Event Register**.

The Accounting Manual expressly requires computerised systems to include controls over system access, operational privileges, an in-built proper audit trail and reliable data backups.  It also requires independent checks, segregation of duties and documentary evidence showing the creation, authorisation, custody, processing and recording of transactions. 

The Manual further requires exception reporting for missing or out-of-sequence accountable documents and requires those exceptions to be investigated and signed off, demonstrating that system exceptions must result in visible and accountable follow-up rather than silently disappearing. 

The current Nexus PIF implementation already uses an `AuditLog::record()` pattern across the codebase and has working audit logging that must remain operational during consolidation into the platform-wide service.

# 2. Core Product Principle

The platform must follow:

> **Business Action → Transaction Commit → Immutable Audit Event → Integrity Protection → Monitoring Projection → Authorised Search and Reporting**

The foundational rule is:

> Audit events are append-only evidence of actions that occurred. They must not be editable business records and must not be used to change the underlying transaction.

# 3. Critical Distinctions

## 3.1 Platform Audit Trail

Records actions occurring within Nexus.

Examples:

* user changed a field;
* approver approved a request;
* administrator granted a role;
* user downloaded a document.

## 3.2 Business Record History

A module-friendly timeline showing relevant events for one record.

Example:

* Leave application submitted;
* HOD recommended;
* HR certified;
* SG approved.

This is a filtered projection of audit events.

## 3.3 Security Log

Records security-sensitive actions and alerts.

Examples:

* failed login;
* MFA reset;
* privileged role granted;
* suspicious export;
* session revoked.

## 3.4 Technical Log

Contains diagnostic information used to operate software.

Examples:

* API error;
* worker exception;
* database timeout.

Technical logs are not automatically authoritative audit evidence.

## 3.5 Internal Audit Module

Manages audit plans, workpapers, findings and corrective actions.

It may inspect Platform Audit Trail events but must not control or alter them.

## 3.6 Analytics

Uses aggregated events for trends and dashboards.

Analytics must not replace the immutable original event record.

* source records;
* business states;

* cancellations;
* reversals.

The Audit Trail records these actions but does not perform them.

## 4.3 Internal Audit owns

* audit engagements;
* findings;
* assurance;
* follow-up verification.

Internal Audit may receive read-only audit-event access.

## 4.4 Security monitoring owns response

The Audit Trail may detect and alert on suspicious activity.

Security/ICT owns:

* investigation;
* containment;
* account suspension;
* incident response;
* escalation.

## 4.5 Observability owns diagnostics

Application metrics, traces and operational logs remain in the observability stack.

Selected security-relevant or business-relevant technical events may also be promoted into the Audit Trail.

# 52. Event Integrity

The system must prevent undetected alteration.

Recommended controls:

* append-only database permissions;
* application-only inserts;
* no ordinary update/delete access;
* cryptographic hash per event;
* event-chain or batch hash;
* periodic signed integrity checkpoints;
* immutable/WORM archival copy;
* restricted database administration;
* integrity-verification jobs.

---

# 53. Hash Chaining

A tamper-evident design may calculate:

`event_hash = hash(previous_hash + canonical_event_payload)`

Requirements:

* canonical serialisation;
* chain scope clearly defined;
* sequence handling;
* restart/recovery process;
* periodic anchor/checkpoint;
* integrity-verification report.

Hash chaining detects changes but does not replace access control or backups.

---

# 57. Event Ingestion Architecture

Recommended flow:

1. Business transaction begins.
2. Business action completes.
3. Audit event is written to a transactional outbox in the same transaction.
4. Event publisher sends it to Audit Trail.
5. Consumer validates schema.
6. Event is appended.
7. event hash created.
8. search and monitoring projections update.
9. outbox marks delivered.

This prevents business changes without corresponding audit events.

# 123. Critical Architecture Rules

The implementation team must treat these as non-negotiable:

> **The Platform Audit Trail is separate from Internal Audit.**

> **Audit events are append-only evidence, not editable business records.**

> **Every material action must identify the actor, subject, time, source and outcome.**

> **Delegated actions must identify both principal and delegate.**

> **Historical actor, position and authority snapshots must not change when profiles change.**

> **Passwords, tokens, MFA secrets, private keys and recovery codes must never be logged.**

> **Audit events must be created only after or atomically with the committed business action.**

> **Critical business transactions must not silently succeed without a durable audit event or outbox record.**

> **Event ingestion must be idempotent.**

> **Denied and failed privileged actions must be logged.**

> **Approvals and signatures must identify the exact record and document versions.**

> **Viewing, previewing, downloading and exporting are different actions.**

> **Audit-log administrators cannot edit or delete individual committed events.**

> **Search access must be purpose-based and itself audited.**

> **Tampering must be detectable through cryptographic integrity controls.**

> **Security alerts are indicators, not proof of wrongdoing.**

> **Audit data must not become employee productivity surveillance.**

> **Legal, audit and investigation holds override normal retention disposal.**

> **Existing working PIF audit logging must remain functional until the shared service passes regression testing.**

# 124. Final Product Rule

An authorised user examining a record should be able to answer:

**Who created it?**
→ actor and timestamp

**Who changed it?**
→ field-change history

**What changed?**
→ previous and new values

**Who approved it?**
→ workflow decision event

**What authority did they use?**
→ authority snapshot

**Were they acting or delegated?**
→ acting/delegation record

**Which version was approved or signed?**
→ record version, document version and hash

**Who viewed or downloaded the supporting documents?**
→ document-access history

**Was any unauthorised action attempted?**
→ denied-event history

An auditor or investigator should be able to answer:

**Is the event record complete?**
→ reconciliation and sequence checks

**Has it been altered?**
→ integrity verification

**Which events belong to the same process?**
→ correlation chain

**What role and authority did the actor hold at that time?**
→ historical actor snapshot

**Can the evidence be exported and independently verified?**
→ forensic evidence package and hashes

**Is the evidence protected from disposal?**
→ legal/audit/investigation hold

That gives Nexus a trustworthy institutional history of who did what, when, under which authority and against which exact record version.
